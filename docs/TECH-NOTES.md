## 1. お問い合わせの受付・メール通知は実現できるか

### 結論：デプロイ先にはほぼ依存しない

「メール送信サーバーを自前で立てる」という発想だとデプロイ先に依存するが、実際は
**メール配信 API サービス**を使うのが標準。HTTP リクエストを投げるだけなので、
Vercel / Cloud Run / VPS のどこでも同じコードで動く。

| サービス | 特徴 |
| --- | --- |
| Resend | 開発者向け。設定が最も簡単。月 3,000 通まで無料 |
| SendGrid | 老舗。無料枠あり。実績重視ならこれ |
| Amazon SES | 最安。ただし初期設定（サンドボックス解除）が面倒 |

### 実装の流れ

1. HP のフォームから antpress の受付 API に POST
2. antpress が内容を **DB に保存**
3. antpress がメール配信 API 経由でクライアントに通知メール送信
4. クライアントは管理画面で問い合わせ一覧も確認できる

### 本当の検討ポイントはデプロイ先ではなく以下 3 つ

| 項目 | 内容 |
| --- | --- |
| 送信元ドメイン | `noreply@antpress.jp` のような独自ドメインが必要。SPF / DKIM の設定をしないと迷惑メール判定される |
| スパム対策 | 公開 API なので必須。Cloudflare Turnstile（無料）＋ IP 単位のレート制限 |
| DB 保存の有無 | メール通知だけだと送信失敗で問い合わせが消える。**DB にも保存すべき** |

### 規模への影響

- 読み取り専用 API に**書き込み API が 1 本増える**
- 問い合わせ一覧画面が 1 つ増える
- スパム対策が必要になる

大きな追加ではあるが、「HP にお問い合わせフォームがあるのに送信先がない」状態は
実務上ありえないため、**入れる前提で考えるのが自然**。

## 2. AI プランの生成エンジン

### 推奨：Claude API（Anthropic）

| モデル | モデル ID | 料金（100万トークンあたり） |
| --- | --- | --- |
| Claude Opus 5 | `claude-opus-5` | 入力 $5 / 出力 $25 |
| Claude Sonnet 5 | `claude-sonnet-5` | 入力 $3 / 出力 $15 |
| Claude Haiku 4.5 | `claude-haiku-4-5` | 入力 $1 / 出力 $5 |

### 1 記事あたりの実コスト試算

原文 2,000 トークン → 生成記事 3,000 トークン程度を想定（日本語で 2,000〜3,000 字の記事）。

| モデル | 1 記事あたり | 円換算（150円/$） |
| --- | --- | --- |
| Opus 5 | $0.085 | 約 13 円 |
| Sonnet 5 | $0.051 | 約 8 円 |

**コストは事実上無視できる水準。** 月 100 記事生成しても 1,000〜1,300 円程度。
品質重視で **Opus 5** を選んで問題ない。

### 実装上のポイント

- 生成は数十秒かかるのでストリーミング表示にする（画面が固まらない）
- 「生成・解析」は非同期処理にして、完了したら結果を反映
- 原文と生成結果は**両方 DB に保存**する（原文を残さないと再生成できない）

## 3. なぜ Next.js を提案したか（理由の訂正と補足）

「メール送信が外部サービスなのでサーバーサイド言語である必要がない」という理解は、
**半分合っているが本質ではない**。実際の理由は次の 4 つ。

| # | 理由 | 重要度 |
| --- | --- | --- |
| 1 | 管理画面（React）と配信 API（Route Handlers）が**同一コードベース**に収まる → モノリス要求に合致 | 高 |
| 2 | **リッチテキストエディタが JS エコシステム**（TipTap / Lexical 等）なのでネイティブに扱える | 高 |
| 3 | AI コーディングの精度が最も高い言語圏 | 中 |
| 4 | Vercel なら運用負荷がほぼゼロ | 中 |

**訂正すべき点：サーバーサイドの重さは「無視できる」わけではない。**
AI 記事生成は数十秒かかるため、Vercel のサーバーレス関数では実行時間制限に当たる可能性がある。
非同期ジョブにするなら Inngest / QStash などのキューサービスを別途足す必要がある。
つまり **Next.js の弱点はまさにこの AI 生成処理**。

## 4. Phoenix LiveView（Elixir）の評価

### 技術的には antpress にかなり良く合う

| 観点 | 評価 |
| --- | --- |
| 管理画面 | ◎ LiveView は CRUD 管理画面が最も得意な領域。antpress の管理画面はまさにこれ |
| **AI 生成の非同期処理** | ◎ **BEAM は常駐プロセス。`Task` で裏で走らせて LiveView に進捗をプッシュするのが標準機能。キューサービス不要** |
| 配信 API | ○ Phoenix は JSON API も普通に書ける |
| PostgreSQL | ◎ Ecto との組み合わせは一級市民 |
| マルチテナント | ○ 問題なし |
| 運用 | ○ Fly.io が定番。Render / VPS も可（Vercel は不可） |

**Next.js の唯一の明確な弱点（AI 生成の非同期処理）を、Phoenix は素の機能で解決する。**
これは偶然ではなく、LiveView が「サーバー側で長時間処理しながら画面を更新する」ために作られているため。

### 弱点

| 観点 | 内容 |
| --- | --- |
| リッチテキストエディタ | △ JS ライブラリを **JS Hook 経由**で組み込む必要がある。可能だが手間。Markdown 中心なら軽減される |
| AI コーディング精度 | △ TypeScript / React に比べ学習データ量が少なく、**反復回数が増える** |
| 学習コスト | △ ただし本人が「勉強がてら」と明言しているため、これは目的の一部 |

### 判断軸

- **納期優先・早くクライアントに提供したい** → Next.js
- **学習も目的・納期に余裕がある** → Phoenix LiveView

antpress は機能スコープが小さく固定なので、Phoenix を選んだ場合のリスクは
一般的な受託案件より低い。

## 5. PostgreSQL の運用先

### まず前提：DB は antpress のコストの中で最小

月額の全体像（小規模運用時）:

| 項目 | 月額目安 |
| --- | --- |
| DB | $0〜25 |
| アプリホスティング | $0〜20 |
| 画像ストレージ | $0〜5 |
| Resend | 無料枠内 |
| Claude API | $5〜10 |
| **合計** | **$30〜60 程度** |

**DB を $25 → $19 に削るために構成を妥協する価値はない。**
それより「クライアントの記事データを失わない」ことの方が事業上はるかに重要。
バックアップが自動で取られるマネージドサービスを選ぶべき。

### 選択肢の整理

| サービス | 評価 |
| --- | --- |
| **Supabase** | ○ 無料枠あり。**ストレージ（S3 互換）も付属**するので画像保存も兼ねられる。バンドル効果が大きい |
| **Neon** | ○ サーバーレス Postgres。無料枠が広く、scale-to-zero で安い。ブランチ機能が便利 |
| Fly.io Managed Postgres | ○ Phoenix を Fly.io に置くなら同一プラットフォームで完結 |
| Railway | ○ 従量課金。最低 $5/月 程度 |
| PlanetScale | ✕ **無料枠が廃止済み**。元々 MySQL 系で、安さ目的の選択肢ではない |
| GCP Cloud SQL | △ 最小構成でも $10〜25/月。安くはないが信頼性は高い |
| VPS 自前構築（Hetzner 等） | ✕ 月 €4 で最安だが、**バックアップ・パッチ適用を自分で負う**。クライアントデータを預かる以上、避けるべき |

### 重要：スタック選択と DB 選択は独立ではない

| アプリ構成 | 相性の良い DB | 理由 |
| --- | --- | --- |
| Next.js（サーバーレス） | **Neon / Supabase** | 接続数が増減するため **コネクションプーラーが必須**。両者とも標準搭載。scale-to-zero も効く |
| Phoenix（常駐プロセス） | **Supabase / Fly.io / Railway** | Ecto が**持続的なコネクションプールを保持**するため、**Neon の scale-to-zero は効かない**（DB が常に起きたままになり、コスト削減効果が消える）。常時稼働型を選ぶ方が素直 |

**つまり「Phoenix ＋ Neon の無料枠で安く」という組み合わせは期待通りにならない。**
Phoenix を選ぶなら Supabase か Fly.io Managed Postgres が素直。

### 推奨

| 構成 | 推奨 |
| --- | --- |
| Next.js を選ぶ場合 | **Neon**（scale-to-zero が効く）＋ 画像は Cloudflare R2 |
| Phoenix を選ぶ場合 | **Supabase**（DB ＋ ストレージを 1 本化）または Fly.io Managed Postgres |

いずれの場合も **Supabase は「DB ＋ 画像ストレージ」を 1 サービスで賄える**点が強い。
管理する外部サービスが 1 つ減るのは、1 人運用では実質的なメリット。

> ⚠️ 各サービスの無料枠・料金は変動が早い。実際に契約する前に最新の料金ページで確認が必要。

## 6. Webhook 機能とは何か

### 問題：SSG は「ビルドした時点の HTML」を配信する

Astro を SSG で使うと、記事一覧の HTML は**ビルド時に生成**され、以後は静的ファイルとして
配信される。antpress 側で記事を公開しても、**HTML は再ビルドされるまで変わらない。**

### 起きること

```
月曜 10:00  ラーメン屋の店主が antpress で「今週の限定メニュー」を公開
月曜 10:01  自分の HP を見に行く → 記事が出ていない
月曜 10:02  「公開したのに出てこないんですけど」と電話がかかってくる
```

HP の HTML は先週生成されたもの。再ビルドを起こす仕組みがないため、
何をしても記事は出てこない。

### Webhook が解決すること

Vercel / Netlify / Cloudflare Pages は **Deploy Hook** という URL を発行できる。
その URL に POST すると再ビルドが走る。

```
1. antpress の管理画面で、クライアントごとに Webhook URL を登録しておく
   （= その HP の Deploy Hook URL）
2. 記事が公開される
3. antpress がその URL に POST する
4. Vercel が再ビルドを開始し、記事が HP に反映される
```

### Webhook がない場合の運用

**クライアントが記事を公開するたびに、運営者が手動で再ビルドを叩く。**

クライアントが 10 社あって各社が月 3 本公開すれば、月 30 回の手作業。
しかも「公開したのに出ない」という連絡を受けてから対応することになる。

### 実装コスト

- `clients` テーブルに `webhook_url` カラム 1 つ
- 記事公開時に POST を 1 本投げる処理

**極小。** microCMS も同等の機能を持っている。

## 7. 基本プランのエディタ選定

### 要件

- **リッチテキストと Markdown を切り替えられる**（3.2 の決定事項）
- LiveView に JS Hook 経由で組み込める（= プレーン JS が望ましい。React 依存だと重い）
- 大きなエコシステムに依存しない

### 候補比較

| 候補 | 切り替え | 依存 | 評価 |
| --- | --- | --- | --- |
| **Toast UI Editor** | **✅ 標準機能** | プレーン JS | **第一候補** |
| EasyMDE | ❌ Markdown のみ | プレーン JS。最軽量 | 切り替え要件を満たさない |
| Quill | ❌ リッチテキストのみ | プレーン JS。成熟 | 切り替え要件を満たさない |
| CodeMirror 6 | ❌ Markdown 寄り | モジュラー | 自前で組む前提なら強いが工数増 |
| Trix | ❌ リッチテキストのみ | プレーン JS。極小 | 切り替え要件を満たさない |
| TipTap / Lexical | △ | React 寄り・大きい | **ユーザー方針により除外** |

### 推奨：Toast UI Editor

**Markdown モードと WYSIWYG モードの切り替えボタンが標準機能として付いている。**
要件（リッチテキスト / Markdown 切り替え）に正面から一致する OSS は実質これだけ。

- ライセンス: Apache-2.0
- プレーン JS で動く（React 不要）→ LiveView の JS Hook と相性がよい
- 画像アップロードのフックも用意されている → Supabase Storage 連携に使える

**確認すべき点**: メンテナンス状況とバンドルサイズは導入前に実測すること。

### ⚠️ LiveView に JS エディタを組み込む際の必須事項

**エディタを載せる要素に `phx-update="ignore"` を付ける。**

LiveView は再レンダリング時に DOM をパッチするため、これを付けないと
**JS が構築したエディタの DOM が破壊される。** JS 制御のエディタを LiveView に
組み込む際の定番の落とし穴。

```heex
<div id="editor" phx-hook="Editor" phx-update="ignore"></div>
```

## 8. レート制限とは何か・閾値の考え方

### レート制限とは

**1 つの API キーが単位時間あたりに投げられるリクエスト数の上限。**
超えたら `429 Too Many Requests` を返す。

### なぜ必要か

利用者が運営者本人だけでも、以下のリスクがある。

| リスク | 内容 |
| --- | --- |
| ビルドスクリプトのバグ | 無限ループで API を叩き続け、Supabase の負荷とコストが跳ね上がる |
| キーの漏洩 | 漏れたキーで大量取得される。レート制限があれば被害が抑えられる |
| DB の保護 | Fly.io / Supabase のリソースを守る |

### ⚠️ 重要：SSG のビルドはバースト的アクセスになる

一般的な「1 分あたり 60 リクエスト」のような制限を掛けると、**ビルドが壊れる。**
SSG のビルドは数秒間に大量のリクエストを投げ、その後は数日間まったく叩かない。
定常レートを前提にした閾値は合わない。

**ただし `API-GUIDE.md` の実装パターンなら、ビルド時のリクエスト数は数本で済む。**
`getStaticPaths` で一覧を 1 回取得し、各記事を props で渡すため、
記事 1 件ごとに fetch する N+1 が発生しない。

### 提案する閾値

| 対象 | 閾値 |
| --- | --- |
| 配信 API（キー単位） | **300 req/min** |
| お問い合わせ受付 API（IP 単位） | **5 req/min**（スパム対策） |

- 配信 API はバーストを許容するため緩めに設定する
- お問い合わせ受付は公開エンドポイントなので厳しくする
- 実際のビルド挙動を計測してから確定する

**この項目はデータモデルに影響しないため、実装段階で決めてよい。**
