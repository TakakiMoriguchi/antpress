## 1. プロダクト概要

- antpress は **microCMS のような立ち位置のサービス**。ただしスキーマは自由定義せず、**必要な機能に固定**する。
- 提供物は 2 つ: **クライアント向け CMS 管理画面** と **コンテンツ配信 API**。
- **マルチテナント前提**。1 つの antpress で複数クライアントのコンテンツをまとめて管理する。
- クライアントごとに**ユーザーを発行**し、そのクライアントのコンテンツだけを編集できるようにする。
- 進め方は「まず要件を固めてから実装」。当面は会話と設計メモの整備に集中し、実装は要件確定後。

### 1.1 想定クライアント

| 種別 | 例 | antpress で管理するもの |
| --- | --- | --- |
| ショップ HP | 街のラーメン屋、美容室、飲食店 | お知らせ・ブログ / 画像 / お問い合わせ |
| コーポレートサイト | 中小企業の会社サイト | ニュース・ブログ / 画像 / お問い合わせ |

**クライアント種別によって機能は変わらない。** 固定スキーマなので、
どちらの種別でも同じ機能セットを提供する。これが 1.2 の設計思想の帰結。

> ⚠️ メニュー管理・店舗情報管理は**機能スコープに含まれない**（3 章参照）。
> それらが必要な場合、HP 側の静的コンテンツとして実装する。

### 1.2 設計思想

- WordPress は「作ろうと思えば何でも作れる」が、**実際に使う機能はだいたい決まっている**。
- antpress はその「よく使うもの」に絞り込み、**過不足のない管理機能**を提供する。
- 自由度を無限に広げるより、**定型パターンを最短で立ち上げられること**を優先する。
- **スキーマの自由度は持たせない**（microCMS との最大の違い）。フィールド定義機能・カスタムスキーマ機能は作らない。
  - 理由: 想定クライアントは街の店舗や中小企業。自由なスキーマ画面を渡しても運用できない。
  - 必要なものは antpress 側が最初から固定で用意する。

### 1.3 運営形態：3 階層の代理店モデル

antpress は**他のエンジニアにも使ってもらう**前提の SaaS。
HP 制作は近場の知り合いに依頼されることが多いため、
**制作者（developer）単位で antpress を提供する。**

```
admin（開発者本人）
  └─ developer（知り合いのエンジニア）
       └─ client（そのエンジニアと契約している店舗・企業）
```

| 階層 | 説明 |
| --- | --- |
| **admin** | 開発者本人。プラットフォーム全体を管理し、developer アカウントを発行する |
| **developer** | HP 制作を行うエンジニア。自分のクライアントを管理する。antpress に年額を支払う |
| **client** | HP のコンテンツを管理する店舗・企業。**developer と契約している** |

#### admin 自身も developer である

**`admins` テーブルは作らない。** `developers` テーブルに `role`（`admin` / `developer`）を
持たせ、**admin 自身も `developers` のレコードを 1 件持つ。**

- 開発者本人も HP を作る（= developer である）ため
- 「admin と直接契約しているクライアント」は
  **「admin 自身の developer レコードに紐づくクライアント」**として表現される
- こうすると `clients.developer_id` が **常に非 NULL** になり、
  「直接契約」の特別扱いがコード全体から消える

`users`（クライアント側アカウント）とはテーブルが分かれたままなので、
テナント間のデータ流出を防ぐ保護（→ `DATA-MODEL.md` 3.1）は維持される。

#### 権限

| | admin | developer | client |
| --- | --- | --- | --- |
| developer の発行・停止 | ✅ | ❌ | ❌ |
| 全体の収益・統計 | ✅ | ❌ | ❌ |
| 自分のクライアント管理 | ✅ | ✅ | ❌ |
| API キー・Webhook 設定 | ✅ | ✅ | ❌ |
| Anthropic API キーの登録 | ✅ | ✅ | ❌ |
| コンテンツ運用 | — | — | ✅ |

- クライアントのセルフサインアップは依然として想定しない。
  **client アカウントは developer が発行する。**

### 1.4 責務の境界

| 領域 | 担当 |
| --- | --- |
| クライアント向け CMS 管理画面 | **antpress が提供** |
| コンテンツ配信 API | **antpress が提供** |
| 実際の HP（フロントエンド） | **antpress の対象外**。案件ごとに別途構築し、API を叩いて表示する |
| 表示テーマ / テンプレート | antpress は持たない |

## 2. 用語定義

| 用語 | 意味 |
| --- | --- |
| **admin** | プラットフォーム運営者（開発者本人）。`developers.role = admin` |
| **developer** | HP 制作を行うエンジニア。自分のクライアントを持ち、antpress に年額を支払う |
| **クライアント（client）** | HP のコンテンツを管理する店舗・企業（テナント単位）。developer に紐づく |
| ユーザー | クライアントに発行するログインアカウント（`owner` / `staff`） |

## 3. 機能スコープ

antpress が持つ機能は以下に限定する。これ以上は増やさない方針。

### 3.1 プラン

クライアント単位で 2 種類のプランを用意する。

| プラン | 内容 |
| --- | --- |
| 基本プラン | 通常のエディタで記事を書く |
| AI プラン | 「原文」を人間がある程度書き、AI が記事として仕上げる |

**AI プランの動作**

1. クライアントは「原文」テキストエリアに下書きを書く（体裁は問わない）。
2. 「生成・解析」ボタンを押す。
3. 原文を元に、**SEO 的に優れ、かつ読みやすい記事**へ自動変換する。

**生成エンジン**

- **Claude API / Claude Sonnet 5**（モデル ID: `claude-sonnet-5`）を使用する。
- **Anthropic の API キーは developer が自分で用意・管理する（BYOK）。**
  - antpress は AI の原価を負担しない
  - → antpress の課金は**サーバー利用料のみ**（→ 3.10）
  - developer 単位でキーを 1 本持つ。クライアント単位では持たない
  - **Anthropic キーが未登録の developer は、クライアントを AI プランに設定できない**
- 原文と生成結果は**両方 DB に保存**する（原文がないと再生成できない）。
- 生成には数十秒かかるため、ストリーミング表示＋非同期処理とする。
- 生成失敗時（キーが無効・残高不足など）は `generation_error` に記録し、
  クライアントには失敗を表示、**developer にも通知する**（キーを直せるのは developer のため）。

> ⚠️ **プラン区分は「antpress の請求額」ではなく「機能フラグ」。**
> AI の原価は developer 持ちなので、antpress → developer の請求はプランで変わらない。
> developer が自分のクライアントにいくら請求するかは developer の商売（antpress の外）。

※ AI プランがあるため、抜粋・SEO フィールドを人が手入力する設計は採らない。

**再生成の履歴は残さない。** 生成をやり直した場合、過去の生成結果は保持せず上書きする。
原文と最新の生成結果のみを保存する。

### 3.2 ブログ

記事のフィールドは以下に**固定**する。

| フィールド | 内容 | 採否 |
| --- | --- | --- |
| タイトル | 記事タイトル | 採用 |
| 本文 | **リッチテキスト / Markdown を切り替え可能** | 採用 |
| スラッグ | URL 用の識別子 | 採用 |
| サムネイル画像 | 一覧・OG 用 | 採用 |
| カテゴリ | 1 つ選択 | 採用 |
| タグ | 複数選択 | **不採用**（→ 下記） |
| 公開状態 | 下書き / 公開 | 採用 |
| 公開日時 | 予約投稿を含む | 採用 |
| 原文 | AI プラン専用。生成の入力元 | 採用（AI プランのみ） |
| 抜粋 | 一覧の要約 | **不採用** |
| SEO（meta description・OG 画像） | 検索対策 | **不採用**（AI 側で担保） |

**カテゴリ**

- クライアントが**自由に作成・編集できる**。
- ただし**どの業種でも使える基本的なものは初期状態で用意しておく**（プリセット）。空の状態から作らせない。
- **1 記事 1 カテゴリ。** 複数選択にはしない。

**タグは作らない**

当初は採用としたが撤回した。理由は 3 つ。

1. **SEO にマイナス。** 記事 20 本規模ではタグページ 1 枚が記事 1〜3 本になり
   thin content になる。同じ記事が複数の URL に現れ、重複コンテンツと
   インデックス膨張を招く。実務では小規模サイトのタグページを `noindex` に
   することが多く、それなら最初から作らない方が筋が通る。
2. **表記が分裂する。** 店舗オーナーが投稿ごとにタグを選ぶと
   「ラーメン」「らーめん」「ラーメン情報」が別タグとして乱立する。
3. **設計思想と一致する。** タグは「存在するが大半のサイトで正しく使われていない
   WordPress 機能」の典型。ここで外さないと 1.2 の思想と食い違う。

Qiita / Zenn でタグが機能するのは記事が数万本あるため。閾値を超えないと逆に働く。
必要になればテーブルを追加する純粋な追加マイグレーションで対応できる。

### 3.3 画像管理

- 記事や各ページで使う画像のアップロード・管理。

### 3.4 お問い合わせ

**フォーム項目の設定**

- 対象項目: 名前 / メール / 電話 / 会社名 / 自由記述
- 各項目について「表示するか」「必須にするか」をクライアントが選ぶ。

**受付と通知**

- HP のフォームから antpress の受付 API に送信される。
- antpress は内容を **DB に保存**する（送信失敗による取りこぼしを防ぐ）。
- 同時に、**antpress に登録してある問い合わせ先メールアドレスへ転送**する。
  - → クライアント設定に「通知先メールアドレス」の項目が必要。
- メール配信は **Resend** を使用する。
- 送信元は独自ドメイン（SPF / DKIM 設定必須）。
- スパム対策を入れる（Cloudflare Turnstile ＋ レート制限）。

### 3.5 アカウント管理

アカウントは 4 種類。**発行は必ず 1 つ上の階層が行う。**

| 種別 | テーブル | 発行者 | 役割 |
| --- | --- | --- | --- |
| **admin** | `developers` (`role: admin`) | （初期投入） | プラットフォーム運営。developer を発行 |
| **developer** | `developers` (`role: developer`) | **admin が発行** | 自分のクライアントを管理。antpress に年額を支払う |
| **オーナー** | `users` (`role: owner`) | **developer が発行** | クライアントの代表。スタッフを発行できる |
| **スタッフ** | `users` (`role: staff`) | **オーナーが発行** | 日常のコンテンツ編集を担当 |

セルフサインアップは一切行わない。

### 3.6 Webhook

記事が公開されたことを、クライアントの HP に通知する。

- クライアント設定に **Webhook URL** を登録する（Vercel / Netlify などの Deploy Hook URL）
- 記事が公開された時点で、その URL に **POST** する
- HP 側で再ビルドが走り、記事が反映される

**採用理由**: Astro を SSG で使う限り、これがないとクライアントが記事を公開しても
HP は更新されない。運営者が毎回手動で再ビルドを叩く運用は成立しない。
既存の HP でも同等の仕組みを使っている。

**責務の境界との関係**: Webhook は HP の表示に一切関与せず「公開されたことを通知する」
だけなので、1.4 の境界を越えない（下書きプレビューを不採用にした理由とは性質が異なる）。

### 3.7 コンテンツ配信 API

別途構築された HP から叩かれる読み取り専用 API。**認証なしのアクセスは一切許可しない。**

#### 前提

**HP 側は API をサーバーサイドから呼ぶ**（Astro のビルド時取得、または SSR）。
ブラウザの JavaScript から叩くとキーが露出し、どの認証方式でも守れないため。
HP を作るのは運営者本人なので、この前提は制御可能。

> ⚠️ 実装ルールと具体的なコードパターンは **`API-GUIDE.md`** に分離した。
> このドキュメントは決定事項のみを扱う。

#### 認証方式

**クライアント単位にスコープされた Bearer API キー**の 1 種類のみ。

- `Authorization: Bearer ap_live_xxxxx` ヘッダで送信
- **クライアント単位にスコープ**する。クライアント A のキーでは A のコンテンツしか読めない
  - → マルチテナント分離がキーのレイヤで完結し、URL の `client_id` を信用する必要がなくなる
- **DB には SHA-256 ハッシュで保存**し、平文は発行時に一度だけ表示
  - キーは高エントロピーなので bcrypt / Argon2 は不要。毎リクエスト検証するため速度が重要
- **1 クライアントに複数キーを発行可能**（本番用 / ステージング用）。片方だけローテーションできる
- キー単位でレート制限と失効を管理
- **公開済みの記事のみを返す。** 下書きは配信 API から一切取得できない

#### CORS は一切許可しない

- CORS ヘッダを返さないことで、**ブラウザからの直接アクセスを構造的に不可能**にする
- 誤ってフロントエンドにキーを書く事故も防げる
- ただし非ブラウザのクライアント（curl 等）には効かない。そこを守るのはキーの役目
- 役割分担: **キー = 認証 / CORS 全閉 = ブラウザ露出の事故防止**

#### 採用しなかった案

| 案 | 理由 |
| --- | --- |
| IP 許可リスト | SSG のビルド時取得ではビルダーの IP が変動するため実運用が困難 |
| Origin 制限 | サーバーサイドからの呼び出しは `Origin` ヘッダを持たないため効かない |
| 署名付きリクエスト（HMAC） | より安全だが HP 側の実装が毎案件で重くなる。キーが露出しない前提では過剰 |

#### API ドキュメント

**Swagger だけでは不足するため、2 つの成果物を用意する。**
OpenAPI は仕様（エンドポイント・スキーマ・認証）を記述できるが、
「React island 内で fetch しない」のような**運用ルールは記述できない**。

| 成果物 | 内容 | 配置 |
| --- | --- | --- |
| **OpenAPI 仕様** | 機械可読な仕様。Swagger UI / Redoc で閲覧 | `/api/openapi`（運営者ログインの後ろ） |
| **API 実装ガイド** | 運用ルール、Astro での取得パターン、アンチパターン | `docs/API-GUIDE.md` |

**OpenAPI は `open_api_spex` で Elixir のコードから生成する。**

- 手書き YAML は必ず実装と乖離するため採らない
- リクエストをスキーマ検証する Plug が付属し、仕様と実装が同期する
- `phoenix_swagger` は Swagger 2.0 世代なので採用しない（OpenAPI 3 を使う）
- API の利用者は運営者本人のみなので、ドキュメントは認証の後ろに置く

### 3.8 スコープ外

- スキーマ / フィールドのカスタム定義
- 表示テーマ、ページビルダー、プラグイン機構
- **クライアントの課金**
  - client → developer の請求は antpress では扱わない。developer の商売の範囲。
  - クライアントのセルフサインアップも行わない（アカウントは developer が発行）。
- **決済機能そのもの**
  - developer への請求は antpress の外で手動で行う（→ 3.10）。
  - **Stripe 連携は実装しない。** 将来 developer が増えた段階で検討（→ 3.9）。
- **下書きプレビュー**
  - 未公開記事を実際の HP のデザインで表示する機能は提供しない。
  - 理由: HP 側に確認用ルートを用意させる必要があり、**「実際の HP は antpress の
    対象外」という責務の境界（1.4）に反する**。自分の HP でどう見えるかは antpress の
    関知するところではない。
- **メニュー管理 / 店舗情報管理**
  - 飲食店のメニュー、営業時間、住所などを管理する機能は作らない。
  - 必要な場合は HP 側の静的コンテンツとして実装する。

### 3.9 将来検討（今は作らないが、将来対応してもよい）

3.8 の「スコープ外」は**作らない方針**のもの。こちらは**時期の問題**で今は作らないもの。

| 機能 | 状況 |
| --- | --- |
| **EC（商品販売）** | ショップ HP のクライアントから求められる場合がありそう。ただし**現時点では対応しない** |
| **Stripe による自動課金** | developer が増えて手動請求・手動回収が負担になった時点で検討（→ 3.10） |

#### EC を将来検討する際の論点

- **固定スキーマの設計と矛盾しない。** EC を足すことは「スキーマのカスタム定義機能を
  作る」ことではなく「商品・注文という固定エンティティを増やす」ことなので、
  1.2 の設計思想はそのまま維持できる。
- **ただし性質が大きく異なる。** EC は「コンテンツ管理」ではなく**「取引管理」**であり、
  決済・在庫・注文・返品対応が絡む。antpress の中に入れるべきか、
  **別プロダクトにすべきか**は、実際に必要になった時点で判断する。
- 上記の理由から、EC を見越して今のデータモデルを複雑にはしない。

### 3.10 課金（developer → antpress）

**antpress に決済機能は実装しない。請求は antpress の外で手動で行う。**

| 項目 | 内容 |
| --- | --- |
| 課金対象 | **developer**（`role: developer`）。admin は課金対象外 |
| 内容 | **サーバー利用料のみ**（AI 原価は developer 持ち → 3.1） |
| 周期 | 年額 |
| 決済 | **antpress の外**（請求書・銀行振込など）。**Stripe 連携は実装しない** |

#### Stripe を実装しない理由

- 対象は**知り合いのエンジニア数名**。この規模に決済システムは過剰
- Stripe を入れると付随物が全部ついてくる:
  Webhook の署名検証、支払い失敗の状態遷移、猶予期間の判定、Customer Portal 連携
- **スモールスタートを妨げる**

#### 手動運用の方が安全という副産物

自動課金だと**カードの有効期限切れで 5 社の HP が同時に落ちる**という最悪のシナリオが
起こり得る。手動なら停止は **admin の意図的な操作のみ**になり、
この事故が構造的に起きない。

#### antpress 側に持つもの

**`developers.status`（`active` / `suspended`）と `note` だけ。**
契約日・請求日・支払い状態のような**状態機械は持たない。**

| カラム | 用途 |
| --- | --- |
| `status` | admin が手動で停止・再開する。これが実質の課金コントロール |
| `note` | admin 専用の自由記述メモ（例: 「2026-09 契約開始 / 年額 ¥X / 振込確認済み」） |

数名規模なら、契約管理はスプレッドシートやカレンダーで足りる。
**antpress の中に作らない。**

#### 停止時の方針

**`suspended` にしたら管理画面と配信 API の両方を止める。** 操作は 1 つ。

| 対象 | 停止時の挙動 |
| --- | --- |
| 管理画面へのログイン（developer / その配下の client） | **停止** |
| 配信 API（その developer の全クライアント） | **停止**（`403` を返す） |

**判断の根拠**

- 停止は **admin の意図的な操作**であり、事前に連絡が取れる相手
  （知り合いのエンジニア）に限られる。予告なく落ちるケースが存在しない
- Stripe を実装しないため、**自動的な停止が起こり得ない**

**実際の影響は「サイトが落ちる」ではなく「更新が止まる」**

HP は Astro の SSG なので、配信 API を止めても**公開中の HP は動き続ける。**

| 対象 | 挙動 |
| --- | --- |
| 公開中の HP | **そのまま動く**（HTML は既にビルド・デプロイ済み） |
| コンテンツ更新 | 止まる |
| 次回のビルド | 失敗する（Vercel / Netlify は**失敗時に前回のデプロイを維持**する） |

> ⚠️ 例外: HP を **SSR** で構築した案件は、配信 API 停止で**即座に表示が壊れる。**
> SSG 前提の判断であることに留意する。

**エラーは意図が読める内容で返す。** 停止時の `403` には
「この developer アカウントは停止されています」と分かるメッセージを含める。
汎用的な認証エラーだと、developer がビルドログを見ても原因が分からない。

#### 未回収リスクについて

決済がないため、**支払わないまま使い続けることを技術的に防げない。**
対象が知り合いのエンジニア数名であれば、信頼関係と手動停止で足りる。
developer が増えて回収が負担になった時点で Stripe を検討する（→ 3.9）。

#### 有料サービス化に伴う要件

| 項目 | 状況 |
| --- | --- |
| **利用規約** | **必要。** 他人の事業データを預かるため、責任範囲を明記すべき |
| 特定商取引法に基づく表記 | オンラインで申込・決済が完結しないため要件は軽くなる。オンライン決済を導入する段階で必要になる |
| インボイス対応 | 請求書を手で発行するため、様式を満たせばよい |
| 稼働率・バックアップ・障害対応 | **要求水準は上がる。** 決済の有無とは無関係 |

> ⚠️ 法務は専門家の確認を推奨。ここは判断材料の整理であり法的助言ではない。

## 4. 技術スタック

| 領域 | 選定 |
| --- | --- |
| アプリケーション | **Elixir / Phoenix（LiveView）** |
| 構成 | **モノリス**（AI コーディング前提） |
| データベース | **PostgreSQL** |
| DB 運用先 | **Supabase** |
| 画像ストレージ | **Supabase Storage**（S3 互換） |
| ホスティング | **Fly.io**（Phoenix の定番） |
| メール配信 | **Resend** |
| AI 生成 | **Claude API / Claude Sonnet 5**（`claude-sonnet-5`） |

### 4.1 Phoenix を選んだ理由

- **AI 生成の非同期処理が素の機能で解決する。** BEAM は常駐プロセスなので、`Task` で
  裏で生成を走らせて LiveView に進捗をプッシュできる。キューサービス（Inngest 等）が不要。
  これは Next.js（サーバーレス）の唯一の明確な弱点だった部分。
- 管理画面が CRUD 中心 → LiveView が最も得意な領域。
- Ecto と PostgreSQL の組み合わせは一級市民。
- 学習目的とも一致する（ユーザーの意図）。

### 4.2 Supabase の使い方

antpress は Supabase を **マネージド PostgreSQL ＋ オブジェクトストレージ**としてのみ使う。

| Supabase 機能 | 使う / 使わない |
| --- | --- |
| PostgreSQL | **使う** |
| Storage | **使う**（画像管理） |
| Auth | 使わない（Phoenix 側で実装） |
| PostgREST（自動 API） | 使わない（Ecto から直接接続） |
| Realtime | 使わない（LiveView があるため不要） |

**採用理由**: DB と画像ストレージを 1 サービスに寄せられる。1 人運用では
管理する外部サービスが 1 つ減ることが実質的なメリットになる。

### 4.3 エディタ

| プラン | 方針 |
| --- | --- |
| 基本プラン | **Toast UI Editor**（OSS / Apache-2.0）を JS Hook 経由で組み込む |
| AI プラン | **自前実装**。TipTap 等のエコシステムは使わない |

**Toast UI Editor を選んだ理由**

- **Markdown モードと WYSIWYG モードの切り替えボタンが標準機能。**
  「リッチテキストと Markdown を切り替え可能」という要件（3.2）に正面から一致する
  OSS は実質これだけだった
- プレーン JS で動く（React 不要）→ LiveView の JS Hook と相性がよい
- 画像アップロードのフックがあり、Supabase Storage 連携に使える

AI プランは「原文の textarea ＋ 生成結果の表示」が中心でリッチエディタを必要としない。

> ⚠️ **LiveView 組み込み時の必須事項**: エディタを載せる要素に **`phx-update="ignore"`**
> を付ける。付けないと LiveView の DOM パッチで JS が構築したエディタが破壊される。
> ```heex
> <div id="editor" phx-hook="Editor" phx-update="ignore"></div>
> ```

### 4.5 レート制限

| 対象 | 閾値 |
| --- | --- |
| 配信 API（**キー単位**） | **300 req/min** |
| お問い合わせ受付 API（**IP 単位**） | **5 req/min** |

- 配信 API は緩く設定する。**SSG のビルドはバースト的アクセスになる**ため、
  一般的な「60 req/min」のような閾値ではビルドが壊れる
- お問い合わせ受付は公開エンドポイントなので厳しくする（スパム対策）

### 4.4 構築時の注意点（実装前に確認すること）

| 項目 | 内容 |
| --- | --- |
| **リージョンを合わせる** | Fly.io は `nrt`（東京）、Supabase も東京リージョンにする。揃えないと全 DB クエリが太平洋を横断してレイテンシが悪化する |
| **Ecto と Supabase プーラー** | Supabase の transaction mode プーラーは prepared statement 非対応。Ecto（Postgrex）は既定で使うため、`prepare: :unnamed` の設定か session mode / 直接接続が必要 |
| 直接接続の IPv6 | Supabase の直接接続は IPv6 が前提になっている場合がある。Fly.io 側の対応と合わせて要確認 |
